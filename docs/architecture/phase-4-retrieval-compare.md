# Phase 4: similarity search and Compare

Phase 4 turns the frozen Phase 3 play embeddings into a product: real nearest-neighbour retrieval in PostgreSQL + pgvector, database-side metadata filters, deterministic evidence for every result, and a synchronized side-by-side Compare view.

Decision: [ADR-0005](../decisions/ADR-0005-pgvector-similarity-retrieval.md). Measurements: [retrieval-v1.md](../evaluation/retrieval-v1.md) (generated by `pnpm retrieval:benchmark`).

```text
data/processed/<ds>/full/embeddings/trajectory-gnn-transformer-v1.parquet   (Phase 3 export, frozen)
data/manifests/<ds>.full.embeddings.trajectory-gnn-transformer-v1.json      (committed manifest)
data/processed/<ds>/full/observed/plays.parquet                             (pre-snap context)
        │  pnpm retrieval:load   validate → COPY → upsert → delete stale → count → ANALYZE (one transaction)
        ▼
PostgreSQL 18.6 + pgvector 0.8.7   (docker compose service "postgres", port 5432)
  schema_migrations · embedding_sets · play_embeddings (vector(128) + HNSW cosine index)
        │  PostgresVectorStore: read-only pool (≤ 4 connections), SET LOCAL per search
        ▼
services/api  RetrievalService ── DescriptorIndex (tracking descriptors, built at startup from Parquet)
  POST /api/v1/search/similar · POST /api/v1/compare · /health (retrieval block) · /api/v1/models (retrieval info)
        │
apps/web  Play view → SimilarPlays · /compare?left&right&align → CompareWorkspace (existing field renderer)
```

```bash

PLAYLENS_SUBSET=full pnpm dev:api

```

Reset (destroys local database state): `docker compose down -v`, then `pnpm db:up && pnpm db:migrate && pnpm retrieval:load`. `pnpm db:down` stops the container and keeps the data. Nothing in normal startup migrates, loads, or resets.

`pnpm db:migrate -- --status` lists applied and pending migrations without applying anything. `pnpm db:status` (or `make db-status`) reports readiness: container, pgvector, migrations, HNSW index, and the embedding count.

The root `Makefile` wraps these: `make dev` runs the whole sequence above (starting Postgres, migrating, and loading a fresh database before starting the API and web app), and `make db-up`, `make db-migrate`, `make db-load`, `make db-verify`, `make retrieval-benchmark`, `make db-reset FORCE=1` map to the commands here. ## Database

- Image `pgvector/pgvector:0.8.7-pg18-trixie` (multi-arch; runs natively on the arm64 Colima VM). Pinned, also used by CI.
- Development credentials `playlens_dev` / `playlens_dev`, database `playlens`, host port `${PLAYLENS_DB_PORT:-5432}`, named volume `postgres_data` mounted at `/var/lib/postgresql` (the PostgreSQL 18 image layout), `pg_isready` health check every 2 s. Default PostgreSQL settings (shared_buffers 128 MB).
- Measured: a cold start including `initdb` became healthy in 6.1 s; a stop and restart with the existing volume took 5.8 s (measured while the host was under heavy unrelated load, 1-minute load average ≈ 18).

### Migrations

Plain SQL files in `services/api/src/playlens_api/retrieval/migrations/`, applied in order by `retrieval/migrate.py`: each in its own transaction under an advisory lock, recorded in `schema_migrations` with a SHA-256 checksum. Editing an applied file is an error, not a silent re-run. No ORM.

| Version | Content |
|---|---|
| 0001 | `CREATE EXTENSION IF NOT EXISTS vector` |
| 0002 | `embedding_sets`, `play_embeddings`, HNSW index |

### Schema

`embedding_sets`, one row per imported export: `model_version` (PK), `dataset_version`, `split_version`, `dimension`, `normalization`, `artifact_path`, `artifact_sha256`, `model_weights_sha256`, `row_count`, `cosine_reference` (JSONB, below), `loaded_at`.

`play_embeddings`, primary key `(play_id, model_version)`:

| Column | Type | Source |
|---|---|---|
| `play_id` | text | PlayLens ID `<game_id>-<play_id>` |
| `model_version` | text, FK → `embedding_sets` | export |
| `dataset_version`, `split_version` | text | export manifest |
| `split` | text, `train` / `validation` / `test` | export (checked against `ml/splits.parquet`) |
| `embedding` | `vector(128)` | export, unchanged |
| `season`, `week`, `quarter`, `down`, `yards_to_go` | smallint | canonical `plays.parquet` (pre-snap) |
| `offense`, `defense` | text | `possession_team`, `defensive_team` |
| `offense_formation` | text | dataset label (pre-snap) |
| `yards_from_own_goal` | real | canonical `line_of_scrimmage_x − 10` |
| `created_at` | timestamptz | |

```sql
CREATE INDEX play_embeddings_embedding_hnsw
    ON play_embeddings USING hnsw (embedding vector_cosine_ops)
    WITH (m = 16, ef_construction = 64);
```

No B-tree indexes on filter columns: at 14k rows a filtered scan takes a few milliseconds, and extra indexes would add plan alternatives without a measured need. Tracking frames, rosters, annotations, and outcomes stay in Parquet; the database holds only what retrieval needs (10.0 MiB table, 11.2 MiB index).

## Ingestion (`pnpm retrieval:load`)

`retrieval/ingest.py` reads the export and its manifest and refuses to load unless every check passes:

| Check | Rule |
|---|---|
| artifact present | otherwise: "Phase 3 embedding artifact not found", with the expected model, path, and the Phase 3 commands. Nothing is created or downloaded. |
| manifest ↔ artifact | file SHA-256 equals the manifest's; manifest and every row name the requested model version |
| dimension | vectors = manifest = database column (`vector(128)`) |
| finite | no NaN / Inf |
| normalisation | every ‖v‖ within 1e-5 of 1 (measured max deviation 1.25e-7) |
| uniqueness | one row per (play, model version) |
| play IDs | well-formed, consistent with `game_id`/`play_id`, present in the processed dataset |
| dataset | manifest dataset version = processed dataset version |
| splits | split labels valid and equal to `ml/splits.parquet`; split version = `splits.json` |
| model | when `artifacts/models/<v>/model.json` exists: weight hash, split version, and embedding dimension match |
| row count | rows = manifest rows; after loading, rows in the database = rows in the export (else rollback) |

Loading is one transaction: upsert `embedding_sets`, `COPY` into a temporary staging table, `INSERT … ON CONFLICT DO UPDATE … WHERE values differ` (unchanged rows are not rewritten), delete rows of that model version missing from the export, verify the count, `ANALYZE`. An interrupted load leaves the previous state. Measured on the full export: a first load inserts 14,108 rows in 13–16 s across runs (14.5 s in the final benchmark; the HNSW graph is maintained row by row, while a bulk index build over the loaded table takes 1.5 s); a rerun reports 0 inserted, 0 updated, 14,108 unchanged, 0 deleted in about 1.8–2 s.

The loader also stores a **cosine reference** for the space: 200,000 seeded random play pairs (mean 0.442, median 0.514, p95 0.906) and every play's exact nearest neighbour (median 0.986, p05 0.967). The API returns it so scores can be read against the space instead of as absolute numbers.

## Retrieval

`retrieval/store.py`. Every search runs in its own read-only transaction; settings use `SET LOCAL` (`set_config(…, true)`) and so never leak between requests. A search refuses to start inside an already open transaction, because `SET LOCAL` lasts until the top-level transaction ends.

- **Metric.** `cosine_distance = embedding <=> query` (pgvector), `cosine_similarity = 1 − cosine_distance`. Vectors are unit length, so this ranks like the dot product.
- **Query vector.** A scalar subquery on the query play's own row; it never leaves the database. A missing row is `embedding_unavailable` (404).
- **Self-match** is excluded in SQL (`play_id <> query`), in both modes and with filters.
- **Model version** is always a predicate; embeddings of different versions are never compared.
- **Exact** (`mode: "exact"`): `enable_indexscan = off`, sequential scan, `ORDER BY distance, play_id LIMIT k`. Deterministic, including ties. This is the ground truth.
- **Approximate** (`mode: "approximate"`, the default): `hnsw.ef_search = max(ef_search, k)` (served `ef_search` = 40, pgvector's default, kept because the benchmark showed no benefit in lowering it), `hnsw.iterative_scan = relaxed_order` (so filters cannot starve the result below k while matches exist, up to `hnsw.max_scan_tuples` = 20,000 > corpus), inner `ORDER BY distance LIMIT k` on the index, outer re-sort by `(distance, play_id)`.
- **Reported plan.** The store runs `EXPLAIN (FORMAT JSON)` on the exact statement and parameters it then executes, and returns `plan: "hnsw_index_scan"` or `"exact_scan"`. Statements are never prepared: a prepared statement may switch to a generic plan different from the one `EXPLAIN` shows (we measured exactly that: a generic plan walked the whole HNSW graph for a filter matching nothing). Under very selective filters PostgreSQL chooses an exact scan; the API then adds a warning that results are exact.
- **Candidates.** With filters, the transaction also counts eligible plays (`retrieval.candidates`), so "fewer than k" is explained ("Only 9 plays match these filters.").
- **Bounds.** `1 ≤ k ≤ 50`; `invalid_k` otherwise. `statement_timeout` = 2 s; pool wait 2 s.

### Filters

A fixed allowlist; each field maps to one parameterised predicate in the same statement as the vector order. Unknown fields, malformed values, and inverted ranges are `invalid_filters` (422). User input never names a column or an ordering.

| Request field | Predicate | Data class |
|---|---|---|
| `down` | `down = %s` | pre-snap |
| `yards_to_go_min` / `_max` | range on `yards_to_go` (1–99) | pre-snap |
| `quarter` | `quarter = %s` (5 = OT) | pre-snap |
| `week_min` / `_max` | range on `week` (1–22) | temporal |
| `offense`, `defense` | team code `^[A-Z]{2,3}$` | pre-snap |
| `offense_formation` | `^[A-Z_]{1,32}$` | dataset label, pre-snap |
| `field_position_min` / `_max` | range on yards from own goal (0–100) | pre-snap |
| `splits` | `split = ANY(%s)` | temporal split |

Coverage and route labels are charted after the play: they appear as evidence (marked †, "not a model input") and are deliberately not filters. Post-play outcomes are neither.

### `POST /api/v1/compare`

Body `{ "left_play_id", "right_play_id", "model_version"? }`. Returns each play's summary, split, frame range and last observed frame; `similarity` (cosine similarity and distance, `right_rank_from_left` and `left_rank_from_right` computed exactly over the unfiltered corpus, the cosine reference) or `similarity_unavailable_reason`/`_code` when retrieval is down or an embedding is missing; `evidence` with IDs `comparison.<group>.<key>`; a role-based `correspondence` (passer ↔ passer, targeted receiver ↔ targeted receiver; "not an assignment"); `descriptor_version`; latency. Frames are not duplicated: the web app reads `/plays/{id}/frames` for each side.

| `database_unavailable` | 503 | no connection within 2 s (then fast-fails for 5 s) |
| `retrieval_unavailable` | 503 | disabled, not migrated, nothing loaded, or embeddings built for another dataset (e.g. the API serves `dev`) |

### Health and models

`/health` gains a `retrieval` block (`ready | unavailable | disabled`, reason, database reachability, PostgreSQL and pgvector versions, schema version, pending migrations, embedding count and versions, HNSW index name), read from a status check cached 30 s (5 s after a failure); no table scans. Overall status is `degraded` when the dataset is missing or retrieval is configured but not ready. `/api/v1/models` sets `retrieval` (representation, cosine, `hnsw`, corpus size) on the model whose embeddings are ready, from the last cached check only.

### Failure behaviour (measured)

With the database container stopped: similarity returns 503 `database_unavailable` in 10–30 ms (a request may wait up to the 2 s pool timeout first, after which failures are served from a 5 s cache); `/plays/*/frames` and `/predict/trajectory` keep returning 200; Compare returns 200 with `similarity: null`, `similarity_unavailable_code: "database_unavailable"` and all 13 evidence records; `/health` is `degraded`. After the database restarts, retrieval recovers within about 7 s (pool connections are checked before use).

### Observability

JSON log lines `retrieval.search` (`request_id`, `query_play_id`, `model_version`, `retrieval_mode`, `plan`, `k`, `filter_count`, `candidates`, `result_count`, `db_latency_ms`, `search_ms`, `total_latency_ms`) and `retrieval.compare` (`request_id`, `left_play_id`, `right_play_id`, `similarity_available`, `evidence_count`, `latency_ms`). Vectors and credentials are never logged; database URLs are redacted.

## Evidence

Evidence records are observations about both plays, kept apart from the retrieval signal (rank and cosine). In search results `left` is the query play. IDs are stable within a response: `<result play_id>.<group>.<key>` in search, `comparison.<group>.<key>` in Compare, so a later Analyst can cite them.

Metadata (relation `same` / `different` / `unavailable`): down, yards to go, quarter, line of scrimmage from own goal (pre-snap); offensive formation, receiver alignment (pre-snap dataset labels); coverage label, targeted receiver route (charted after the play, marked †). None is a model input; agreement is context, not the reason for similarity.

Structural descriptors (`ml/src/playlens_ml/descriptors/structural.py`, version `structural-v1`), computed from canonical observed tracking (yards; offense attacks +x; y across the field), with the tracked players only (no linemen, no pass rushers, no ball in this release):

| Key | Frame | Definition |
|---|---|---|
| `offense_width` | last observed frame | max(y) − min(y) over tracked offensive players (needs ≥ 2) |
| `deepest_defender_depth` | last observed frame | max(x) over tracked defenders − line of scrimmage |
| `target_depth` | last observed frame | targeted receiver x − line of scrimmage (negative = behind) |
| `target_separation` | last observed frame | distance from the targeted receiver to the nearest tracked defender |
| `mean_speed` | last 2.0 s (20 frames) | mean tracked speed over all tracked players and frames in the window |

The last observed frame is where the dataset's input window ends and the trajectory model forecasts from; the 2.0 s window is the span the encoder reads. These are deterministic summaries, not explanations of what the embedding encodes and not statements of intent. Missing values carry a reason (e.g. the one play with no tracked defender). The API computes all of them once at startup with one streaming pass over the tracking Parquet (0.35–1.2 s, about +35 MB peak) and serves lookups; the same function computes one play on demand (tested equal).

## Compare

`/compare?left=<id>&right=<id>&align=<mode>` reuses the existing field renderer, overlays, replay dock, and timeline. The two plays usually have different lengths (8–123 observed frames), so "synced" is defined explicitly:

| Mode | Master time τ → each play | When paused |
|---|---|---|
| `progress` (default) | p = τ / D with D the longer play's duration; play time = first + p × duration | frame `round(p × (frames − 1))` |
| `origin` | seconds relative to each play's last observed frame | nearest real frame at that time |
| `start` | seconds from each play's first observed frame | same |
| `snap`, `phase` | snap-relative / event-anchored; offered only when both plays have those events (this dataset has none) | same |

In `progress` both plays start together (0%) and reach their last observed frame together (100%); the longer play runs at real speed and the shorter one is slowed. During playback the renderer interpolates for smooth motion; paused, stepped, or scrubbed, each side shows a real frame (`lib/compare/sync.ts`). Frame lines show `Frame n (i of N)` for each side and mark the last observed frame.

Controls: Play/Pause, previous/next frame, Reset, "Last observed" (both plays to their last observed frame), speed (0.25–2×), the shared timeline (keyboard-scrubbable slider with per-side lanes), and a **Sync** switch (`role="switch"`, labelled on/off). Sync off gives each play its own dock and clock starting at the frame it was showing; sync on resumes from the left play's position. The mode menu sits in the header with the similarity summary (`#rank nearest to the left play of N · cosine x`).

The evidence panel shows the embedding sentence (both ranks, cosine, the space's reference medians), a context table (field / left / right / relation) and a tracking-measure table (left / right / signed delta with units, definitions on focus or hover), and a "Show that frame" action. Failure states: an unknown or failing play affects only its own column (the other stays playable); a failing compare request shows Retry and leaves both replays; the same play on both sides shows a warning. Below `lg` the fields stack vertically; on phones one field with a Left/Right switch.

## Measured performance (summary)

From [retrieval-v1.md](../evaluation/retrieval-v1.md): 600 split-stratified query plays, warm cache, client on the host over localhost TCP, host 1-minute load average 23 at the start (unrelated background load; medians are stable, tails are noisy).

| Operation | p50 | p95 | p99 |
|---|---:|---:|---:|
| Exact search statement (k = 10) | 4.6 ms | 5.2 ms | 6.4 ms |
| HNSW search statement (k = 10, ef_search 40) | 1.2 ms | 2.6 ms | 6.0 ms |
| Exact store call (lookups + search) | 8.0 ms | 9.5 ms | 12.9 ms |
| HNSW store call (lookups + EXPLAIN + search) | 6.5 ms | 13.5 ms | 32.1 ms |
| `POST /search/similar`, approximate, server side | 8.7 ms | 11.6 ms | 37.2 ms |
| `POST /search/similar`, exact, server side | 11.0 ms | 13.1 ms | 15.8 ms |
| `POST /search/similar`, approximate + same down | 12.8 ms | 15.5 ms | 19.5 ms |
| `POST /compare`, server side | 12.9 ms | 15.9 ms | 21.2 ms |

HNSW recall@5/10/20 against exact search was 1.000 for every `ef_search` in {10, 20, 40, 64, 100, 200} and in every filtered scenario with matches (no query returned fewer neighbours than available). Exact pgvector search matched the NumPy reference in 1,080 of 1,080 searches (max distance difference 2.8e-7). With iterative scans off (diagnostic), results come back short (k = 10, ef_search = 10: recall 0.900, every query one result short because the self-match consumes a candidate), which is why iterative scans are always on.

## Similar Plays (Play view)

"Find similar plays" runs the real search for the open play (k = 10, approximate by default; a segmented control switches to the exact scan). Filter chips are derived from the play's own context: same down, distance ±2 yd, same quarter, same formation, same offense. Toggling a chip reruns the database query; "Clear filters" resets. Each row leads with the rank (`#1`), then matchup, play ID, split (train / validation / held-out test), clock, down and distance, formation; up to three shared-metadata items in words (charted labels marked †); two tracking measures (query → result); the cosine value, visually secondary and never a percentage, marked "below the median random pair" when it is; **Open** (carries `?similar_to=` so the opened play offers "Compare with …") and **Compare**. States: stable skeleton while loading; empty ("No similar plays matched these filters. Try broadening the filters." with Clear); retrieval down ("Similar-play retrieval is temporarily unavailable." with the reason and Retry); missing embedding (stated, nothing substituted); other errors with Retry.

## Limitations

- One season (2023), 14,108 passing plays, partial tracking (no linemen, pass rushers, or ball).
- Similarity is closeness of a representation learned for **trajectory prediction** over the last 2.0 s before the forecast origin. It is not coaching equivalence and not a judgement that two plays are tactically the same. Phase 3 showed the graph layers did not measurably improve forecasts over a temporal-only model; the served embedding is still the pre-registered GNN + Transformer model.
- The space is anisotropic: nearest neighbours typically score 0.97–0.99 and random pairs average 0.44 with a wide spread. Absolute cosine values are not calibrated probabilities; rank and evidence carry more meaning, and under restrictive filters the nearest matching play can be farther than a typical random pair (the UI says so).
- HNSW does reduce database retrieval latency here (search statement 1.2 vs 4.6 ms at the median and 2.6 vs 5.2 ms at p95; server-side search 8.7 vs 11.0 ms at the median), with identical recall. At about 14k vectors the practical benefit is modest: the exact scan is already a few milliseconds, the saving is a small share of a request, and under very selective filters the advantage disappears. The index matters more as the corpus grows, and it is always evaluated against exact search.
- Metadata filters cover pre-snap context and split only; charted labels are evidence, not filters.
- Structural descriptors summarise one frame or a 2 s window of tracked players; they do not explain the embedding or player intent.
- "Synced" means normalized progress (or real time from a chosen anchor). The dataset has no snap/throw events, so there is no semantic phase alignment.
- The trajectory model's embedding of a play's own forecast origin defines retrieval; plays with very short observed windows (8 frames) are front-padded by the encoder, as in Phase 3.

## Future work (not done in Phase 4)

- A centered (or whitened) embedding set as a separate, explicitly versioned experiment, evaluated offline against v1 for label agreement and neighbour stability.
- Retrieval with the temporal-only ablation's embeddings, to see whether the graph layers matter for neighbourhoods even though they did not for forecasts.
- A partial HNSW index per model version once a second embedding set is served.
- Surfacing ANN recall and label agreement on the Evaluation page's retrieval section.
